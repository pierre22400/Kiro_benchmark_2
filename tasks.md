# Implementation Tasks — Evidence Timeline CLI

## Governance gates

- [ ] **G0 — Preserve specification baseline.** Confirm `specblock`, `requirements.md`, and `design.md` are committed, pushed, and clean before creating code. No implementation begins until this task file is itself validated, committed, and pushed.
- [ ] **G1 — Apply checkpoint discipline to every phase.** Before every commit: run `git status --short`, `git diff --check`, the phase’s targeted verification, and only stage named phase files. Commit and push immediately. Record targeted checks, applicable global-suite status, integration failures, and unexecuted checks in the phase record.
- [ ] **G2 — Maintain concrete interface inventory.** After every implemented module, update `docs/interface-inventory.md` with the actual module path, callable names, parameter types, returned contract, public failures, filesystem effects, and updated call graph. Commit and push that inventory before beginning a dependent module.

## Sequential implementation phases

- [ ] **1. Bootstrap the import-safe package and executable boundary.** Create only the packaging metadata, `src/evidence_timeline/__init__.py`, `__main__.py`, and a minimal `cli.py` skeleton that is inert on import. Establish `evidence-timeline` as the executable name without adding domain behavior. Update the interface inventory with the entrypoint-to-CLI edge before any dependent code. Targeted verification: Python 3.11.15 compilation and imports with no stdout/stderr or filesystem effects. Global verification: run the applicable repository suite if one exists; otherwise record it as not applicable. Checkpoint example: `impl: bootstrap import-safe CLI package`.

- [ ] **2. Define immutable shared contracts and timestamp normalization.** Implement `contracts.py` first, containing only the exact shared request, event, payload, result, failure, and dictionary-conversion contracts from the design. Implement `timestamps.py` second against those contracts, covering all accepted RFC3339 forms, UTC normalization, offset comparisons, invalid dates/offsets, and rejected leap seconds. Do not create parser, timeline, or CLI business behavior in this phase. Update/push the interface inventory after `contracts.py`, then after `timestamps.py`; do not work on these two shared-contract modules in parallel. Targeted verification: compilation/import, normalized timestamp examples, and invalid timestamp rejection through the public helper. Checkpoint example: `impl: add shared event contracts and timestamps`.

- [ ] **3. Implement safe incremental input and single-record parsing.** Implement `input_reader.py` with file/stdin selection, incremental UTF-8 physical-line handling, path and symlink rejection, and `local-io` logical failures. Then implement `jsonl_parser.py` using `contracts.py` and `timestamps.py` to produce one valid `Event` or one exact `RecordError` per physical line, including duplicate-ID tracking. Update and push the interface inventory after the reader, before the parser; then update it again after the parser. Targeted verification: blank lines, malformed JSON, finite-object enforcement, exact key set, type/enum/tag rules, line numbers, UTF-8 failure, duplicate IDs, and no input mutation. Checkpoint example: `impl: add incremental JSONL parsing`.

- [ ] **4. Implement pure timeline operations.** Implement `timeline.py` only after the concrete Event contract is inventoried and pushed. Provide exact-code-point event ordering, all-AND summary filters, complete severity counts, deterministic case summaries, and explain’s one-neighbour context selection. It must receive Events and return logical payloads or `event-not-found`; it must not read files or emit streams. Update/push its inventory and call graph before building its caller. Targeted verification: timestamp/case/event tie ordering, each filter, combined filters, empty summaries, counts containing all keys, and each explain boundary. Checkpoint example: `impl: add deterministic timeline operations`.

- [ ] **5. Implement redaction and deterministic rendering.** Implement `redaction.py` before `rendering.py`; preserve the specified replacement order and scope. Implement `rendering.py` with the exact text lines and canonical JSON options, returning content without the final LF. It consumes shared payload contracts and cannot perform stream or filesystem I/O. Update/push the inventory after redaction and again after rendering before any caller depends on it. Targeted verification: canonical JSON key ordering/UTF-8/no NaN, every text payload form, one LF applied by the caller only, and ordered redaction including consistent redacted case IDs. Checkpoint example: `impl: add canonical renderers and redaction`.

- [ ] **6. Implement output target preflight and authorized atomic writing.** Implement `output_writer.py` after rendering’s exact byte contract is locked and recorded. Preflight must resolve relative paths from the start cwd, reject directories/symlinks/symlink ancestors without mutation, and precede input opening. The writer alone creates allowed parent directories, writes a temporary sibling, flushes/closes, atomically replaces an existing regular target, and cleans temporary files best-effort on failure. Update/push its inventory before wiring it into the CLI. Targeted verification: stdout-mode no mutation, missing-parent success only after rendered bytes exist, target-byte identity, invalid targets, replacement preservation before completion, and local-I/O mapping. Checkpoint example: `impl: add safe output writer`.

- [ ] **7. Orchestrate domain operations.** Implement `operations.py` sequentially after input/parser, timeline, and payload contracts are all frozen in the inventory. `validate` scans all physical lines; `summarize` and `explain` fail fast at the first invalid line; `schema` performs no input I/O. Keep `invalid-jsonl`, `event-not-found`, validate-invalid result, and input local-I/O as logical outputs. Update/push its inventory before the CLI integration phase. Targeted verification: complete validation payload/count, fail-fast line/code, no output request capability in operations, schema no-read behavior, and operation result/status mapping. Checkpoint example: `impl: add validation and timeline orchestration`.

- [ ] **8. Complete the CLI adapter and end-to-end wiring.** Extend `cli.py` only after all called interfaces are concrete, documented, committed, and pushed. Implement exact command grammar, help fragments, `allow_abbrev=False`, controlled usage failures, request normalization, output-target preflight, single application-operation invocation, rendering, stream emission, output delegation, and exit mapping. Finalize `__main__.py` without import-time execution. Update/push the final call graph and interface inventory. Targeted verification: no arguments/help, every command/options matrix, stdin `-`, errors/precedence, output suppression under `--output`, and no `--redact` JSON path. Checkpoint example: `impl: complete CLI lifecycle`.

- [ ] **9. Verify the applicable integrated system without changing interfaces to force compatibility.** Run the full available repository suite and a command-level acceptance pass covering valid/invalid validation, summary filtering, explain context and absent ID, schema, text/JSON output, redaction, stdin, output paths, determinism, input immutability, and import safety. If an interface discrepancy appears, checkpoint it before modifying any verification or test fixture. Classify results as targeted successes, global successes, pre-existing/integration failures, or unexecuted. Checkpoint example: `checkpoint: integration verification complete; global suite status recorded`.

## Dependency and concurrency rule

Phases 1–9 execute in order. No phase may run in parallel with a phase that creates, changes, or consumes the same Event, Request, payload, failure, persistence boundary, output byte, or service interface. A phase may begin only after its predecessor’s code, interface inventory/call graph, targeted verification, checkpoint, and push are complete.

## Definition of implementation completion

A phase is not complete merely because its targeted verification passes. It becomes integrated only after its applicable global suite passes. If no global suite exists, the phase record must explicitly state that fact and include the end-to-end command-level verification performed; it must not claim global-suite success.
